## 0-1. 시스템 구성 (발표 도입부용)

### 3단 구조

```
[프론트(React)] ──WebSocket──▶ [백엔드(FastAPI, 순수 중계)] ──WebSocket──▶ [코랩 서버(FastAPI+GPU)]
  아바타 타일 4개                  URL 관리만 담당                TTS + MuseTalk 립싱크 생성
  MediaSource로 재생                                            (cloudflared 터널로 외부 노출)
```

- **백엔드는 아무 연산도 안 한다** — 코랩 URL(재기동마다 바뀜)을 한 곳에서만
  관리하려는 목적의 순수 릴레이
- **프레임은 완성되는 즉시 흘려보낸다** — 영상 파일이 다 만들어질 때까지 안 기다림
  (이게 "실시간 스트리밍"의 핵심)

### 규모

| 항목 | 수량 |
|---|---|
| 아바타 위원 | **4명** (2명 → 4명 확장) |
| 위원당 영상 | **3개** (대기 루프 1 + 제스처 2) = 총 **12개** |
| 위원 후보 풀 | 8명 (도메인마다 4명씩 배정) |
| TTS 보이스 | 4개 (Kelee K / Harry / Gihong / Han) |

### 아바타 슬롯 배정 방식 (설계 포인트)

아바타 얼굴·목소리 자산은 **4개로 한정**돼 있는데, 위원 구성은 **문서 종류마다
LLM이 다르게 뽑는다**. 특정 위원(`business_strategy` 등)에 얼굴을 고정했더니
"이번 회의에 그 위원이 없어서 창이 비는" 문제가 실제로 발생.

→ **"회의 내 등장 순서"로 슬롯을 동적 배정**하도록 변경.
코랩의 얼굴·목소리는 "역할을 연기하는 배우"처럼 다루고,
실제 위원 정체성(이름/색/자막)은 화면 표시에서만 정확히 유지.
도메인마다 항상 정확히 4명이 나오는 걸 확인했기 때문에, 순서 기반이면 **어느 도메인이든 항상 완전 커버**.

| 구간 | 시간 | 문제점 |

| 원본 영상 프레임 추출(ffmpeg) | 2.14초 | 같은 페르소나면 항상 동일 |
| **좌표/랜드마크 준비** | **26.39초** | 캐시를 켰는데도 241장을 매번 재읽기 |
| 프레임별 VAE latent 인코딩(241장) | 5.02초 | 같은 페르소나면 항상 동일 |
| **배치 루프 진입 전 합계** | **47.42초** | |

**핵심 발견**: 같은 페르소나에 대해 **TTS 문장과 무관하게 항상 같은 결과가 나오는 계산에
33.55초를 매 요청마다 다시 쓰고 있었다.**

### 1-3. 페르소나 캐싱 효과 (시도 3)

### 1-4. 모델 상주 구조 효과 (시도 5)

## 2. 생성 속도 개선 — 0.3배속 → 1.6~1.8배속

### 2-1. 문제 정의 (시도 7)

12초짜리 응답을 만드는 데 **40.7초** 소요 = 실제 재생 속도의 **0.3배속**.
첫 화면이 빨리 떠도 재생이 금방 생성 속도를 따라잡아 계속 멈추는 구조적 문제.

### 2-2. 배치 크기 확대 — 효과 없음 (중요한 반증)

배치 크기 8 → 16으로 늘려도 **프레임당 처리 시간이 0.082~0.083초로 동일**.
→ GPU 배칭 효율 문제가 아니라 **프레임당 CPU 비용이 고정 병목**이라는 걸 증명.
(GPU를 더 굴려도 소용없다는 결론)

### 2-3. 실제 원인과 3가지 조치 (시도 8)

MuseTalk 소스를 직접 받아 확인한 결과, **매 프레임마다 얼굴 파싱(FaceParsing)
신경망을 다시 실행**하고 있었음. 얼굴 위치가 고정된 페르소나에서는 불필요한 반복.

| 조치 | 내용 | 누적 생성 속도 |
|---|---|---|
| (개선 전) | 매 프레임 `get_image()` 풀 파이프라인 | 0.3배속 |
| **조치 1+2** | 마스크 사전계산 + PIL-free 블렌딩(`_blend_fast`) | **0.8배속** |
| **조치 3** | PNG 압축 왕복 제거 → rawvideo 직접 전달 | **1.6~1.8배속** |

**최종 실측**: 16프레임 배치를 0.35~0.36초에 처리
(17배치=272프레임/6.32초, 22배치=352프레임/8.0초)

> 세션 전체에서 **가장 큰 단일 개선** — 실시간보다 느리던 걸 실시간보다 빠르게 만듦

## 3. 버퍼링(끊김) 해결

### 3-1. 진짜 병목은 서버가 아니라 네트워크였다 (시도 9)

생성 속도가 1.6~1.8배속으로 빨라졌는데도 재생은 계속 끊김.
전송 구간에 계측(`[SEND-TIMING]`)을 붙여 확인:

- `ws.send_bytes()` 자체 소요: **항상 0.0초** (서버 안에서는 전혀 안 느림)
- 서버가 측정한 "전체 완료"(13.79초) vs 클라이언트 실제 마지막 데이터 수신(41.9초)
- **약 28초 차이** → 병목은 **Cloudflare Quick Tunnel(무료 터널)의 네트워크 구간**

**검증 실험**: 비트레이트를 낮췄더니(전송량 4.6배 감소) 버퍼링이 완전히 사라짐 → 가설 확정

### 3-2. 화질/안정성 절충점 탐색 (시도 10)

| 해상도 / crf | 총 전송량(실측) | 버퍼링 |
|---|---|---|
| 720x1280 / crf20 (최초값) | 3.85MB | 반복(6~7초 주기) |
| **480x854 / crf28 (채택)** | **838KB~1.14MB** | **0회** |
| 576x1024 / crf24 | 1.14~1.57MB | 짧게 1회 |

### 3-3. 클라이언트 버퍼 임계값 튜닝

| `RESUME_THRESHOLD` | 결과 |
|---|---|
| 2.0초 | 안정적이나 초반 대기가 김 |
| **0.3초** | **오히려 버퍼링 급증 (11초 동안 7회)** — 너무 낮으면 네트워크 편차를 못 버팀 |
| 0.8초 | 초반 대기 0.7~0.8초 + 버퍼링 0회 (당시 최적) |
| 1.5초 (현재) | tail 페이싱 제거 후 전송 패턴이 바뀌어 재상향 |

### 3-4. tail 페이싱 제거 — 요청 소요 8~24초 → 3.7~3.8초

무음 tail(원본 루프 영상 그대로 이어붙이는 부분, **GPU 연산 없음**)까지
발화 프레임과 똑같이 실시간 배속으로 천천히 보내던 게 원인.
특히 **짧은 문장일수록 tail이 최대 241프레임까지 길게 붙어** 더 심했음.

→ tail은 페이싱 없이 즉시 전송하도록 수정. **요청 전체 소요 8~24초 → 3.7~3.8초**

### 3-5. 동시 생성 방지 + 인코딩 preset (시도 11, 2026-07-26)

| 원인 | 실측 | 조치 |
|---|---|---|
| 동시 생성 충돌 | 재생 중 스트림의 청크 도착 간격이 **약 2배(580ms → 1100ms)로 악화** | 프론트에 전역 생성 게이트 추가 — 코랩이 `done` 보낼 때까지 다음 요청 보류 |
| 인코딩 preset | `-preset ultrafast`는 같은 crf에서 압축 효율이 낮아 전송량 증가 | `veryfast`로 변경 |

→ 실사용 테스트에서 버퍼링 해결 확인

## 4. TTS 엔진 비교 — OpenAI vs ElevenLabs

### 4-1. 순수 TTS 속도 비교 (MuseTalk 없이 단독 측정)

| 엔진 | 속도 | 한국어 품질 | 채택 여부 |
|---|---|---|---|
| OpenAI `gpt-4o-mini-tts` | **2~3초** (기준) | 양호 | 1차 채택 → 변경 |
| **ElevenLabs `eleven_multilingual_v2`** | **OpenAI 대비 1.5~2배 빠름** | 만족 (립싱크까지 붙여 청취 확인) | ✅ **최종 채택** |
| ElevenLabs `eleven_flash_v2_5` | **OpenAI 대비 4~7.5배 빠름** | 음질이 조금씩 깨짐 | ❌ 기각 (속도보다 품질 우선) |
| Zonos-v0.1 | GPU 버그로 CPU 폴백 시 **11~12분/문장** | 한국어 비공식 지원 | ❌ 보류 |
| ZONOS2 | 첫 호출 46초(워밍업) → 이후 6~13초대 | 텍스트 정규화 실패 사례 확인 | ❌ 보류 |

### 4-2. 가장 중요한 발견 — TTS는 병목이 아니었다

> "TTS 생성 속도를 줄이자"가 원래 목적이었는데, 실제로 재보니
> **진짜 병목은 TTS가 아니라 MuseTalk 프레임 생성 자체(전체 소요의 80%+)**였다.

- 초기 TTS 지연 실측: 5.8~6.9초 → 최적화 후 파이프라인에서 TTS 비중 2.5~4.6초
- **TTS 엔진 교체만으로는 체감 속도가 크게 안 바뀜** — 그럼에도 채택한 이유는
  품질이 만족스럽고 어차피 개선되는 부분이기 때문

## 5. 입모양/자세 자연스러움 개선

### 5-1. 원본 영상(제스처 영상) 프롬프트 개선 — 가장 효과적이었던 것

MuseTalk은 **코 부리~턱 랜드마크로 크롭 영역을 계산**하고, **입 부분을 통째로 덮어씌운다**.
이 특성을 근거로 원본 영상 생성 프롬프트를 여러 차례 수정:

| 문제 | 원인 | 해결 |
|---|---|---|
| 필기 동작 중 얼굴이 거의 안 보임 | 시선이 카메라를 벗어나면 랜드마크 기준 크롭 영역이 어긋남 (공식 `BBOX_SHIFT.md`로 근거 확인) | 필기 동작·펜/소품 완전 제거, 시선 카메라 고정 |
| 정지사진처럼 부자연스러움 | "머리 완전 고정" 지시가 호흡 등 자연스러운 움직임까지 죽임 | **시선·고개(고정)와 몸의 자연스러움(호흡·손동작)을 분리해서 지시** |
| 원본 입이 계속 움직여 립싱크 방해 | "설명하는/발표하는" 프레이밍이 입을 계속 움직이게 만듦 | **"말 안 하고 제스처만 하는 상황"으로 재구성** |
| 손동작이 너무 없음 | 고정 지시가 과함 | "계속 작게 움직이는 리듬" 추가 |

### 5-2. 이음매(전환 지점) 개선

| 문제 | 원인 | 해결 | 시점 |
|---|---|---|---|
| 발화→대기루프 전환 시 자세 튐 | idle 영상이 독립적으로 돌아서 stream 종료 시점의 idle 프레임 위치가 우연에 달림 | `finish()` 시 idle을 0번 프레임으로 seek + `seeked` 이벤트 대기(300ms 타임아웃 안전장치) 후 전환 | 07-19 |
| **tail 시작 지점 제스처 순간이동** | 발화는 ping-pong 인덱싱인데 tail은 `video_num % loop_len`으로 **전혀 다른 위치를 새로 계산** (예: 182번 → 59번으로 점프) | tail도 `frame_list_cycle` 인덱싱을 그대로 이어가도록 수정 | **07-25** |
| 대기 루프 복귀 시 화면 정지 | 크롬이 반복되는 `video.play()`를 전력절약 정책으로 거부 (한 번은 **147초간** 안 풀림) | idle/stream `<video>` 태그 2개로 분리, idle은 마운트 후 절대 재호출 안 함 | 07-18 |

**tail 순간이동 버그 검증 방법**: 제보된 영상을 프레임 단위(초당 12장)로 잘라서 확인 →
0.6~0.7초 사이 **단일 프레임 컷**으로 점프 확정

### 5-3. 우글거림(jitter) 완화 — 시도했으나 실서비스 미반영

> ⚠️ **발표 시 주의**: 이 항목은 "했다"고 말하면 안 된다. **실험은 했지만
> 검증도 불확실하고 실제 서비스 코드에는 반영조차 안 된 상태**다.

**문제 정의**: MuseTalk이 입 영역을 VAE로 새로 합성하는 과정에서
① 원본 영상과 미묘하게 색감이 달라지고 ② 프레임마다 미세하게 떨려 보이는(시간축 jitter) 현상

**시도한 3가지** (`musetalk_setup.ipynb` 9번 섹션, 2026-07-15):

| 방법 | 구현 내용 | 실서비스 반영 |
|---|---|---|
| **① `extra_margin` 조정** | 크롭 하단 여유를 15로 설정 | ✅ **반영됨** (현재도 사용 중) |
| ② 입 주변 색보정 | 원본 영상 입 주변(200×120px) 색 평균을 기준으로 프레임별 offset 보정, **타원형 마스크로 페더링**해서 사각형 경계가 안 보이게 처리 | ❌ 미반영 |
| ③ 프레임 시간축 스무딩 | 이웃 프레임과 가중 블렌딩 (이전 0.15 / 현재 0.70 / 다음 0.15) | ❌ 미반영 |

**왜 반영이 안 됐나 (2026-07-16에 발견한 2가지 문제)**:

1. **검증 자체가 불확실**: 이 실험은 `scripts.inference` CLI 경로(노트북 8번 섹션)의
   결과물을 입력으로 받는데, 그 경로가 **`os.system()`을 써서 실패해도 조용히 넘어가는
   버그**가 있었음 → 애초에 제대로 된 입력으로 실험이 돌았는지조차 확신 불가

2. **경로 자체가 다름**: 실제 서비스는 `app.py`의 `run_inference_sync()`를 쓰는데,
   이 실험은 완전히 다른 CLI 경로 기반이라 **코드가 서비스에 들어가 있지도 않음**

> **교훈**: "결과물 품질에 확신이 없다면, 개선 방법을 더 찾기 전에
> **실험이 애초에 제대로 돌았는지**부터 의심해야 한다"

**현재 실서비스에 적용된 우글거림 관련 설정** (파라미터뿐):

| 파라미터 | 값 | 의미 |
|---|---|---|
| `VERSION` | v1.5 | 공식 권장 버전 (v1.0 대신) |
| `EXTRA_MARGIN` | 15 | 크롭 하단 여유 — **우글거림 대응으로 조정된 유일한 실반영 항목** |
| `PARSING_MODE` | `jaw` | 얼굴 파싱 모드 |
| `LEFT/RIGHT_CHEEK_WIDTH` | 90 | 볼 영역 폭 |
| `BATCH_SIZE` | 16 | (속도엔 영향 없음이 실측으로 확인됨) |
| `PACE_SPEED_MULTIPLIER` | 1.5 | 재생 속도보다 1.5배 빠르게 전달해 버퍼 축적 |

**남은 작업**: 실제 서비스 경로(`app.py`)로 새로 뽑은 결과물 기준으로 우글거림 재평가 →
필요하면 색보정/스무딩을 `run_inference_sync()`에 맞게 새로 구현

### 5-4. ⚠️ 미해결 — 발화 시작/끝 입모양

**증상**: 립싱크가 첫 프레임부터 입을 벌린 채로 시작하고, 끝날 때 마지막 발음 모양 그대로 멈춤

**근본 원인 (코드로 증명)**: `get_whisper_chunk`에서 `audio_padding_length_left=2` 설정 때문에
**frame 0은 이미 내부적으로 0벡터(무음과 동등)만 참조**하는데도 입을 벌린 채로 나옴
→ **모델이 "무음 → 닫힌 입"을 애초에 학습하지 않았다**는 뜻

**시도한 방법과 결과 (2026-07-26)**:

| 방법 | 결과 | 실패 이유 |
|---|---|---|
| 무음 패딩 (300ms까지) | ❌ | frame 0이 애초에 오디오를 안 봄 (위 근본 원인) |
| 오디오 페이드인/아웃 (`afade`) | ❌ | 같은 이유 |
| 알파블렌딩 크로스페이드 (linear/smoothstep, 4~18프레임) | ❌ | 서로 다른 입모양 두 장을 정렬 없이 섞으면 중간 알파에서 **이중노출** 필연 |
| optical flow 워핑(모핑) | ❌ | 닫힌 입에 없던 **이빨이 새로 나타나는 disocclusion** — flow가 표현 불가, 뭉개짐 |
| 마스크 가중 블렌딩 | ❌ | 블렌딩 범위를 입 주변으로 좁혔지만 이중노출 자체는 그대로 |
| 하드컷(블렌딩 없이 전환) | ❌ | 점프컷처럼 보여 시도 전 기각 |
| **파인튜닝** | **보류** | 공식 학습 요구사양이 **8x H20 GPU(GPU당 74~85GB)** — 시간·자원 제약 |

**결론**: 추론 시점(inference-time) 후처리로 해결 가능한 방법은 사실상 소진.
블렌딩 계열은 전부 "서로 다른 입모양 두 장을 섞는다"는 같은 한계에 부딪히고,
오디오 조작 계열은 "모델이 frame 0에서 오디오를 안 본다"는 구조 때문에 애초에 무효.
**근본 해결은 학습 단계(파인튜닝)에서만 가능**하다는 것이 이번 검증의 결론.

**현재 서비스 반영 상태**: 시작 지점 블렌딩은 **적용하지 않음**(원본 그대로).
어설픈 블렌딩이 오히려 더 어색하다는 게 실험으로 확인됐기 때문.
tail 순간이동 버그 수정(5-2)만 반영된 상태.

**파인튜닝 사전 검증 결과 (2026-07-26)**: 실행 자체는 가능함을 확인
- V1.5 체크포인트(`unet.pth` → `pytorch_model.bin` 리네임)가 학습 코드에 정상 로드됨 (849.9M 파라미터)
- Colab A100 80GB 단일 GPU에서 OOM 없이 학습 루프 진입 확인
- 실제 학습 데이터(HDTF 400개 영상) 전처리에 **영상 40개 → 302조각 → 3~4시간** 소요 예상되어 이번엔 중단
- **참고 발견**: 원본 학습 코드에 무음 근처(오디오-영상 싱크 낮은) 샘플의 gradient를
  깎거나 0으로 만드는 `adapted_weight` 로직이 있음 → 이게 애초에 이 문제가 생긴 원인이자,
  파인튜닝 시 `sync_loss: 0`으로 꺼야 하는 이유

## 6. 안정성 개선 (버그 수정)

| 버그 | 원인 | 해결 |
|---|---|---|
| 발화 도중 연결 끊기고 다음 위원 끼어듦 | WebSocket keepalive 핑퐁 타임아웃(기본 20초) — 코랩이 GPU로 바쁘면 핑 응답 못 해 "죽었다"고 오판. **양방향으로 각각 존재** | 백엔드: `ping_interval=None` / 코랩: `--ws-ping-interval 86400` |
| 발화 안 끝났는데 배지 꺼지고 다음 위원 등장 | `tts_end` 신호를 "도착 즉시" 반영 — 데이터는 항상 재생 위치보다 앞서 도착 | 신호에 `speech_seconds` 포함, `video.currentTime`이 실제로 그 지점 지날 때만 반영 |
| C 발언 중인데 D가 먼저 시작 (**4명 이상에서만 재현**) | 전환 게이트에 소유자 개념이 없어, 늦게 끝난 위원의 정리 로직이 이미 넘어간 게이트를 덮어씀 | 게이트에 `owner` 추가 — 게이트 주인 본인만 열고 닫게 제한 |
| 영상은 나오는데 소리 안 남 | **코드 문제가 아니라 VSCode 내장 브라우저(웹뷰)에서 테스트 중이었음** | 실제 크롬에서 테스트 |
| 같은 발언 요청이 최대 3번 중복 발생 | React StrictMode로 `useEffect`가 분석 요청을 두 번 보냄 | 요청 중복 방지 가드 추가 |

**최종 안정성 검증**: 4명 회의 + 3명 채팅 답변(최대 **59.7초짜리 발화** 포함)
전부 연결 끊김 없이 정상 완료

## 7. 발표 시 강조하면 좋을 포인트

1. **"측정하지 않으면 못 고친다"** — 74초 중 69초가 어디서 쓰이는지 몰랐다가,
   단계별 계측 로그를 붙이고 나서야 진짜 병목(랜드마크 재계산 26.39초)을 찾음

2. **"짐작한 원인이 3번 틀렸다"**
   - 배치 인터리브(시도 1) → 효과 미미, 원인 오진단
   - 배치 크기 확대 → 프레임당 시간 동일, GPU 문제 아님을 증명
   - "서버가 느려서" → 계측해보니 서버는 0.0초, 무료 터널 대역폭이 진짜 원인

3. **"목적과 실제 병목이 달랐다"** — TTS 속도를 줄이려 엔진을 바꿨지만,
   실측해보니 병목은 MuseTalk 생성(80%+)이었음. 그래도 품질 개선은 얻음

4. **"인원이 적을 땐 안 드러나는 버그"** — 게이트 겹침 버그는 위원 2명일 땐 절대 재현 안 되고
   4명으로 늘려야만 나타남

5. **불가능을 코드로 증명** — 발화 시작 입모양 문제는 여러 방법을 시도한 끝에,
   `get_whisper_chunk` 소스를 직접 읽어 "모델이 애초에 학습 안 한 것"임을 확인.
   추측이 아니라 근거로 한계를 규명함
