# 1. 프로젝트 개요

## 1. 표지

### 제목

**AI Review Board**

### 부제

공모전 준비 전 과정을 지원하는 근거 기반 AI 심사위원 워크벤치

### 하단

팀명 / 팀원 / 제출일

## 2. 공모전 준비에는 서로 연결되지 않는 세 가지 어려움이 있다

### 핵심 문제

1. 공고문과 평가 기준을 해석하기 어렵다.
2. 아이디어 단계에서 기획과 기술 관점을 함께 검증하기 어렵다.
3. 문서를 작성한 뒤에도 어느 부분을 왜 수정해야 하는지 알기 어렵다.

### 기존 방식의 한계

- 일반 생성형 AI는 해당 공모전의 공식 기준과 실제 자료를 충분히 반영하지 못한다.
- 결과가 긴 텍스트로 제공되어 원문의 수정 위치를 찾기 어렵다.
- 평가를 반복해도 이전 피드백과 개선 이력이 연결되지 않는다.

### 발표 문장

“우리는 단순한 AI 첨삭이 아니라, 공모전의 공식 기준과 원문 근거를 따라가며 기획 전후를 연결하는 서비스를 만들었습니다.”

## 3. 작성 전 아이디어 발굴과 작성 후 문서 평가를 하나의 서비스로 연결했다

```text
공모전 정보 입력
        ↓
공고문·신청서·수상작 분석
        ↓
┌────────────────────┬────────────────────┐
│ 작성 전             │ 작성 후             │
│ 아이디어 발굴        │ 기획서 업로드        │
│ 기획·개발 위원 토론 │ 문서 위 AI 피드백    │
│ 신청서 초안 생성     │ 점수·근거·수정 제안  │
└────────────────────┴────────────────────┘
        ↓
수정·재평가·버전별 개선 추적
```

### 핵심 가치

- 공고문과 심사기준을 최우선 근거로 사용
- 기획 위원과 개발 위원의 역할을 분리
- 피드백을 원문 위치 및 인용 근거와 연결
- LLM 의견과 규칙 기반 점수 계산을 분리

## 4. 사용자는 문서를 쓰기 전과 쓴 후 모두 같은 프로젝트 안에서 지원받는다

### 작성 전

```text
공고 입력 → 공모전 분석 → 문제 발굴 → 아이디어 토론
→ 콘셉트 확정 → 신청서 항목별 초안
```

### 작성 후

```text
기획서 업로드 → RAG 검색 → AI 위원 병렬 심사
→ 규칙 기반 채점 → 문서 위 피드백 → 수정본 비교
```

### 결과물

- 공모전 핵심 의도와 평가 포인트
- 문제 정의·대상·해결안·기대효과·검증 방법
- 기준별 점수와 근거
- 수정 우선순위 및 문단별 제안
- 버전별 점수·해결 여부 변화

## 5. UI·API·AI 오케스트레이션·데이터 계층으로 시스템을 분리했다

## 12. 36개 검색 테스트셋에서 모든 질의의 정답 문서를 Top-5 안에 검색했다

### 테스트 설정

| 항목 | 내용 |
| --- | --- |
| 데이터셋 | `rag_eval_current_v6_36` |
| 케이스 수 | 36 |
| 검색 범위 | Top-5 |
| 컬렉션 | `project_documents_kure_v6` |
| 비교 조건 | 문서 유형 라우팅 적용 전·후 |

### 결과

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| Recall@5 | 0.9444 | 1.0000 | +0.0556 |
| Hit@5 | 0.9444 | 1.0000 | +0.0556 |
| MRR@5 | 미기록 | 1.0000 | 최종 측정 추가 |
| 검색 실패율 | 0.0000 | 0.0000 | 유지 |
| 평균 검색시간 | 305.1ms | 288.6ms | 5.4% 감소 |

### 해석

- 개선 전 실패했던 제출 조건·파일명 형식 질의가 문서 유형 라우팅 후 검색됐다.
- 정답 문서가 단순히 Top-5에 포함된 것을 넘어 모든 케이스에서 첫 순위로 검색됐다.
- 검색 정확도와 함께 평균 검색시간도 16.5ms 감소했다.

### 반드시 표기할 제한

**현재 36개 케이스는 `human_verified=false`인 참고 평가다. 정식 성능 주장 전 원문 기준 사람 검수가 필요하다.**

## 13. RAGAS 관점에서 검색과 생성을 분리 평가하도록 설계했다

### RAGAS 대응 지표

| 평가 영역 | 프로젝트 지표 | 현재 상태 |
| --- | --- | --- |
| Context Recall | Recall@5 | 참고 측정 완료 |
| Context Precision | 다중 문서 근거 적합도 | 평가 코드 지원 |
| Answer Faithfulness | Faithfulness | LLM Judge 지원, 최종 실측 필요 |
| Answer Relevance | 0~4점 relevance rubric | 추가 권장 |
| Hallucination | Hallucination Rate | 평가 코드 지원, 최종 실측 필요 |
| 역할 적합도 | Persona Evidence Fit | LLM Judge 지원, 최종 실측 필요 |
| 인용 정확도 | Citation Precision | 다중 문서 gate 지원 |

### 품질 목표

```text
Recall@5             ≥ 0.85
Hit@5                ≥ 0.90
MRR@5                ≥ 0.80
Faithfulness         ≥ 0.90
Hallucination Rate   ≤ 0.05
Persona Evidence Fit ≥ 0.80
Citation Precision   ≥ 0.90
```

### 제출 전 해야 할 정식 평가

1. 36개 데이터셋을 사람 검수하여 `human_verified=true`로 변경
2. 생성 평가를 실행해 Faithfulness·Hallucination·Persona Fit 측정
3. 가능하면 공식 `ragas` 패키지 결과와 내부 지표를 함께 제시
4. 실패 케이스 2~3건과 개선 조치를 결과 해석에 포함

### 주의

현재 저장소에는 RAGAS와 유사한 지표 체계 및 자체 평가기가 있으나, 확인된 리포트는 검색 평가 중심이다.  
따라서 현 단계 PPT 제목은 **“RAG/RAGAS 대응 평가”**로 쓰고, 정식 RAGAS 실행 전에는 “RAGAS 최종 점수”라고 표기하지 않는다.

### 현재 코드·로그에서 확인되는 내용

- LLM 노드·attempt·성공/실패·원본 응답을 선택적으로 기록
- RAG 검색 건수, 적격 근거 수, 발언 주입 수, grounding 결과 기록
- 서버 실측 참고: 전체 분석 약 29~41초

- 위원 검토 LLM 약 13~27초
- 위원장 종합 약 10~16초
- 문서 색인 약 20~90초로 가장 큰 체감 병목

### 비용 계산식

# 5. 자체 평가 의견

## 18. 팀 회고서 — 계약 중심의 병렬 개발은 잘 작동했고 통합 가시성은 더 필요했다

### 협업이 잘된 점

- 역할 경계를 Frontend·Backend·RAG·LangGraph·Media로 명확히 나눴다.
- 공통 JSON Schema와 Mock 데이터로 실제 통합 전에도 병렬 개발할 수 있었다.
- 담당 영역 밖 변경은 Devlog와 요청 문서로 이유와 영향을 공유했다.
- 실제 API·LLM·NCP 환경에서 문제를 재현하고 수정했다.
- 실패 사례와 기술적 의사결정을 코드 주석과 문서에 축적했다.

### 개선할 점

- 서비스 방향 변경 시 초기 아키텍처 문서와 실제 구현의 차이가 커졌다.
- 여러 팀원이 같은 통합 파일을 수정하면서 충돌과 중복 구현이 발생했다.
- 로컬과 NCP 환경 차이로 동일 기능의 검증 결과가 달라지는 경우가 있었다.
- 기능 개발에 비해 비용·TTFB·정식 RAGAS 같은 운영 지표 수집이 늦었다.
- 담당자 영역을 넘는 긴급 수정의 승인·리뷰 절차를 더 명확히 할 필요가 있다.

### 다음 프로젝트에서 적용할 개선

1. 매주 아키텍처·API 계약 동기화 시간 운영
2. 통합 브랜치의 자동 E2E와 배포 후 smoke test 의무화
3. 관측성 요구사항을 기능 요구사항과 동시에 정의
4. 주요 기능마다 담당자와 리뷰어를 함께 지정
5. 서비스 방향 변경 시 기존 문서에 legacy 표시 후 최신 문서로 단일화

### 개인 자기 평가서 작성 템플릿

각 팀원은 다음 5문항을 1페이지 이내로 작성한다.

1. 내가 맡은 목표와 실제 구현 범위
2. 가장 어려웠던 문제와 해결 과정
3. 다른 파트와의 협업 기여
4. 정량적 결과 또는 검증 근거
5. 아쉬운 점과 다음 프로젝트에서의 개선 계획

### 최종 결론

**AI Review Board는 여러 AI를 보여주는 서비스가 아니라, 서로 다른 전문 판단을 공식 심사기준과 원문 근거에 연결하고 사용자의 실제 수정 행동까지 이어 주는 서비스다.**
