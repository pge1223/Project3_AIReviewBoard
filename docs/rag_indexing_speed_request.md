  색인이 **문서 간 직렬 큐**로 돌아서 여러 파일을 한 번에 올리면 뒤 문서 대기가 누적됩니다.

## 왜 중요한가 (사용자 여정 기준)

수정본 1개를 제출하면 대기 = **색인 ~50초 + 분석 ~30-40초** — 색인이 총 대기의 절반
이상입니다. 버전 추적 데모(v1.0→v1.3 4회 제출) 한 사이클이면 색인 대기만 ~3분입니다.
분석 쪽은 위원 LLM 병렬·위원장 백그라운드 분리·rubric 캐시 수리로 더 짜낼 여지가 작아서,
남은 큰 덩어리는 색인입니다.

## 관찰 (해석은 용준님께)

- 청크당 0.46~1.2초로 편차가 크고, **44청크(51.9s)와 108청크(49.5s)가 비슷한 ~50초** —
  청크 수와 비선형이라 배치 크기/max_length/스레드 설정에 따라 여지가 있어 보입니다.
- 서버는 GPU 없음(CPU 추론). 모델 로드는 상주 상태라 로드 시간은 아닙니다.

## 요청 (방법 선택은 용준님 판단)

1. KURE 인코딩 **배치·스레드 설정 점검** (위 비선형 실측 참고)
2. **CPU 추론 최적화** 검토 — int8 양자화 / ONNX·OpenVINO 등 (검색 품질·스키마 불변 전제)
3. (참고) 문서 간 직렬 큐 — 같은 CPU 경합이라 병렬화 효과는 제한적일 수 있어 판단에 맡깁니다

청킹 v5 재색인(페이지 경계 소제목 수정으로 붙임2 재색인 필요)과 겹치는 작업이라,
같이 반영되면 재색인 검증을 한 번에 할 수 있습니다.
